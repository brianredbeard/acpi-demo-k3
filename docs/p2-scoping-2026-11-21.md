# P2 scoping (2026-11-21) — against the qualified P0+P1 base

The board runs P0 (dispatch, type-0 WFI, _LPI, UFS, display
Phase 1) + P1 (ownership model, sequencer, gate, rate policy) —
all reproducible from source, payload-diff verified per flash.

## P2 items, scoped

### Device-domain power operations (ESOS)
Coordinated resource transitions for qualified devices via RPMI.
Foundation: the P1 ownership model + the rate policy are the
coordination primitives. What's missing: per-device resource
descriptors (clock/reset/isolation lists) and the RPMI DEVICE
service group wiring. Dependency: the 0x11000000 idle state as
a dtb variable (the gate's end-to-end proof) — recommended as
the FIRST post-P1 cycle since it also unlocks the _LPI index-2
decision.
Estimate: the model + service wiring is bounded work on the
repaired pipeline; device descriptors are per-device data
collection.

### Performance-control backend (Both: CPPC)
Qualified frequency/voltage transitions + SBI CPPC. Foundation:
the rate policy's allowlist IS the qualification mechanism;
voltage coordination needs the regulator framework (already
port-proven in ESOS: regulator_fixed, spacemit_regulator_probe).
The CPPC ACPI tables (_CPC) exist in the DSDT already (CPPC
revision check pending). Dependency: per-domain voltage
sequencing rules (P1-grade audit work).
Estimate: medium — the policy layer extends naturally.

### Laptop EC coordination (ESOS)
EC boundary for lid/power/charger/battery/thermal/wake. The
cros_ec_espi probe currently DEFERS (GpioInt -517) on this
board — the EC stack is present but its interrupt resource
isn't wired. This is a DSDT/EC-firmware question BEFORE any
ESOS work: the EC's GpioInt needs a correct _CRS/GpioInt
declaration. First step: diagnose the -517 (a GPIO controller
dependency, likely the PRP0001:07 gpio device ordering).
Estimate: diagnostic first; ESOS-side work is bounded after.

### System-suspend implementation (Both, if selected)
SBI system suspend as a separate contract from HSM. The vendor
syssusp path EXISTS in the ESOS source (k3-os0_sysreset.c +
the syssusp ops with the M2 coordination) — unqualified. The P1
sequencer is exactly the missing coordination layer. This is
the largest P2 item and directly builds on the sequencer.
Estimate: large; recommend after device-domain (P2 #1).

## Recommended order

1. The 0x11000000 idle state (dtb variable) — unlocks the

2. Device-domain power ops (P2 #1)
3. EC GpioInt diagnosis (cheap, unblocks P2 #3)

All on the repaired pipeline: build_esos.py + original dtbs

## P2 #3 rescope (post-root-cause, 2026-11-21 rhct2 boot)

The -517 is ROOT-CAUSED and was never a DSDT defect: the EC
driver (built-in, probes at 1.9s) depends on the GPIO
controller driver (module, udev-loaded at 31.9s) — a
built-in-vs-module packaging deadlock the kernel's defer
window cannot bridge. The GpioInt (pin 43, bank1 pin11,
\\_SB.GPIO) declaration is correct; the fix is the GPIO
driver as a first-class ACPI citizen (=y + immutable irqchip
+ quiesce, patch series in patches/kernel-gpio/), built and
awaiting deployment.

CORRECTED BOUNDARY ANALYSIS (the scoping's "DSDT question
first" premise is retired):

LINUX OWNS the EC entirely — cros_ec_espi over the eSPI
peripheral channel, the PR memmap window (0x84000000), the
GpioInt event line, cros-ec-pwm -> pwm-fan, keyboard/backlight
if wired. ESOS HAS NO eSPI stack (verified: zero cros-ec
references in the tree) and should not grow one.

ESOS's P2 #3 slice is exactly three things:
1. DEVICE-POWER GATING of EC-dependent domains — the fan
   (FAN0, PWM-consumer) rides the DISPLAY-class? NO: the fan
   is thermal infrastructure, its natural class is MGMT-
   adjacent. Decision needed: a K3_CONSUMER_THERMAL class or
   MGMT-hold (the fan must run when ESOS thermal policy says
   so, regardless of AP state).
2. WAKE SOURCES: EC events (lid/power button via the GpioInt)
   must reach the sleeping harts — the P1 wake path
   (timer/IPI/UART qualified) extends with the GPIO IRQ as a
   wake source once the kernel fix binds the EC (the GIC line
   43 -> APLIC wake routing is the qualification item).
3. SYSTEM-SUSPEND INTERACTION (P2 #4 dependency): syssusp
   entry must not occur while the EC expects AP eSPI
   responses (the eSPI peripheral channel's suspend contract
   — host alert/signal requirements across S0-like states).

What P2 #3 is NOT: EC firmware work, EC command
interpretation, or battery/charger policy in ESOS. Those are
Linux's (cros_ec stack) once bound.

Next concrete step after the kernel cycle lands: enumerate
the live EC surface (cros-ec chardev, PWM channels, the fan's
thermal trip points) and wire the FAN0 device-power decision
into patch 0009's owner map.

## P2 #2 progress: CPPC service group (patch 0010)

The RPMI CPPC backend, following the qualified service
patterns:

- k3-os0_cppc.c: the platform ops (get_reg/set_reg per hart,
  update_perf, get_current_freq) over the RPMI_CPPC_* register
  namespace. SINGLE-POINT DOMAIN: highest=nominal=lowest=2500
  (the CCU PLL tables carry one rate each — cluster DVFS is
  not a qualified path). desired/min/max accepted+recorded;
  update_perf acknowledges and holds nominal. The interface
  is real; the transitions stay conservative — the P1
  rate-policy philosophy applied to the perf domain.
- spacemit-hsm.c: the created rpmi_hsm context is now shared
  (spacemit_rpmi_get_hsm_ctx) — the CPPC group needs
  hart-id<->index translation from the live HSM topology.
- glue slot (k3-os0-rpmi-cppc compatible) + the dtb node
  (rpmi-cppc@14; source-tree only — the shipped FIT dtbs
  come from the qualified bundle, untouched).

_CPC (the ACPI side, CPPC_ENABLE-gated in Cpu.asl): FFH
encodings VALIDATED against the RISC-V FFH spec Table 6 —
type-1 SBI CPPC regs 0x5 (desired), 0xB (reference counter),
0xD (perf limited) + one type-2 CSR (0xC00 = the cycle
counter). Enabling _CPC ships as a separate variable once
the service is flash-qualified (the kernel-side SBI CPPC
shim for FFH is absent in 6.12 — the kernel reads _CPC via
SystemMemory FFH emulation or not at all; enable only after
the runtime path is proven).

Built via build_esos.py from the lock (10 patches);
rpmi_cppc_func exported, library calls relocated. Flash
qualification pending.

## p2q1 on-target qualification — attempt 1 post-mortem

The regression gates PASSED on p2q1 (17 clocks, 3 LPI, UFS,
clean boot — the gate does not disturb boot).

The device-power/CPPC client tests hit a structural wall:
the Linux mpxy mailbox channel (8, RPMI proto) is exclusively
owned by the built-in clk-rpmi driver. Attempts:
1. Raw SBI MPXY ecalls: wrong layer (msg_id is the 8-bit
   service id; the framing lives in the mailbox layer) —
   timeouts.
2. Kernel mailbox client from a runtime module: "mailbox
   not free" (single-owner channels).
3. TEMPORARY UNBIND of clk-rpmi to free the channel: KERNEL
   PANIC — unbinding the clock driver with live deviceless
   consumers tears down in-use clocks (my reasoning ignored
   the clk framework's teardown path). One reboot lost, no
   data. RECORDED as a hard rule: never unbind clk-rpmi on
   a running system.

THE CORRECT PATH (attempt 2, not yet run): the qualification
client as a first-class citizen — a DSDT test device (the
RCLK pattern: its own "mboxes = <MPXY, 8, 0>" spec) + a small
kernel driver that binds to it from boot, owning its own
channel. This is a firmware+kernel variable pair: the DSDT
device + the test driver, one qualification cycle.

The service-side behavior is unchanged and build-verified;
only the client plumbing needs the proper shape.

## System suspend qualification update (2026-11-22, v4 firmware)

ENTER: QUALIFIED. `echo mem > /sys/power/state` freezes all
tasks, suspends consoles, drops board power 17W -> 14.2W
(Kauf plug evidence). The P1 sequencer + ESOS syssusp path
(OpenSBI rpmi-system-suspend backend) work end to end.

EXIT: OPEN — no wake source armed. Tried: power button,
USB keyboard, Wake-on-LAN (magic packet to the GMAC). All
inert; recovery required a cold power cycle.

Wake path design: the EC is alive in suspend (the ownership
model) and OpenSBI lists rpmi-pwrkey — the gap is the ACPI
GpioInt wake capability (the EC's power-button IRQ needs a
wakeup-capable flag so the kernel arms it as a wake source)
plus possibly rpmi-pwrkey event routing. Next kernel/firmware
cycle item; test = suspend, press power button, expect resume
with uptime preserved.
