# K3 8250 console registration in cycle 3e

**The packaged quirk omits `UPF_FIXED_TYPE`.** The 3d/3e investigation treated hardware type detection as disabled. In EL10-284, `serial8250_register_8250_port()` sets `UPF_BOOT_AUTOCONF` on the registered port and copies the supplied type only when the caller sets `UPF_FIXED_TYPE`. Without that bit, `uart_configure_port()` resets the type to `PORT_UNKNOWN` and requests `UART_CONFIG_TYPE`. The 8250 driver then runs hardware detection if its resource request succeeds. `UPF_SKIP_TEST` skips the loopback test and leaves other register accesses enabled. ## How this could stop serial output

The packaged 3e config disables `CONFIG_SERIAL_8250_16550A_VARIANTS`, and the quirk does not request a full probe. On the normal FIFO-equipped 16550A classification path, the driver consequently selects the generic FIFO capabilities. Its final `serial8250_clear_IER()` writes zero to the interrupt-enable register. The XScale capability set includes `UART_CAP_UUE`, which makes that function preserve the unit-enable bit. On K3, clearing IER bit 6 stops the transmitter after its current byte. OpenSBI's UART writer waits for transmit readiness without a timeout. Thus even an SBI boot console can lose output when Linux reprograms the physical UART. This is a source-supported mechanism. No trace yet identifies that write as the last retiring instruction. [EL10 classification](</tmp/uart284.wfsJvm/linux-6.12.0-284.el10/drivers/tty/serial/8250/8250_port.c:969>) · [IER handling](</tmp/uart284.wfsJvm/linux-6.12.0-284.el10/drivers/tty/serial/8250/8250_port.c:692>) · [K3 register manual](</home/bharring/Projects/spacemit-docs-chip/en/key_stone/k3/k3_docs/k3_usermanual/14_connectivity/uart.md:355>) · [OpenSBI UART writer](../../opensbi-reset-queue-diagnostic/lib/utils/serial/uart8250.c)

IRQ 11 proves resource translation succeeded. TTY activation normally requests the interrupt later. Registration can first remove an existing legacy port and print a console-disabled message before configuring the new port. The partial prefix alone cannot establish that the new console's first write or an interrupt handler ran. The rhct13 COM0 resource supplies the 256-byte register range, GSI 42, stride four, 32-bit access and clock frequency. The Linux property reader succeeded and the working board uses that same base, IRQ and base baud. ## Discriminating test

1. In the `intel,xscale-uart` match branch, directly after `uart.port.type = PORT_XSCALE;`, add `uart.port.flags |= UPF_FIXED_TYPE;`. A one-line diff was checked against the instrumented 3e input. Verify bit 27 on the compatible-match branch in the resulting image and identify it by digest. Keep IRQ 11, the firmware tables and the initramfs inputs matched across the experiment. [One-line diff](</tmp/k3-8250-review.AUvMad/3e-fixed-type.patch>)
2. Control baud explicitly. The recorded 3e trial used bare `console=ttyS0`; the name-based 284 console setup defaults to 9600 when no options are supplied. Firmware SPCR and the working gpioy boot specify 115200. For a no-rebuild control, run the existing 3e image at `console=ttyS0,115200n8`, retaining `earlycon=sbi keep_bootcon`, then use that same command line with the one-line candidate. Removing `console=` still allows SPCR to nominate the UART. [3e command line](</tmp/k3-serial-full.log:167428>) · [EL10 console setup](</tmp/uart284.wfsJvm/linux-6.12.0-284.el10/drivers/tty/serial/8250/8250_port.c:3447>)
3. Look for `is a XScale`, the registration-return marker, serial getty input/output, and a separately identified boot over SSH or a persistent per-boot journal. If serial still cuts off, locate the boundary between removal of the old port, configuration, and console enable using a trace independent of COM0. A live write via `/dev/mem` changes the UART shared with SBI and cannot distinguish those stages.

For an image supporting both local NVMe and software iSCSI root, retire both local overrides and generate a separately named image against the 3f module tree, explicitly including the dracut `iscsi` module. Carry the onboard GMAC and its dependencies, initramfs networking, `iscsiadm`, `iscsid`, the SCSI disk driver and the root filesystem driver. Keep the local NVMe boot arguments free of network-root requirements. Use a separate boot entry for the iSCSI target. Gate kernel-install output on transport dependency resolution inside the final image, then qualify the same image with local NVMe and with a designated iSCSI root LUN. iSCSI data volumes attached after local boot require the installed initiator and modules on the real root. The 3f incident did not exercise target login or root on iSCSI.
