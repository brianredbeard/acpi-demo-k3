# Pico rhct12 and the build-5 kernel RPM

**Build 5 passed mock packaging and failed ACPI boot in the eSPI bus driver.** The board built `6.12.0-284.acpidebug.1.el10.riscv64` in 34 minutes. The kernel, kernel-core, kernel-modules and kernel-modules-core RPMs were installed. The input SRPM SHA-256 was `9267fb1f5808905badb7613f596d6401afd8d6013c9cad39c50dcc2eeace92f1`. The kernel-core RPM SHA-256 was `76baaa6c0373a7d27829771f7dc71b60ea83b92ef494362d835e37891074a253`. The result directory's build.log appends multiple attempts. The build-5 section begins at line 11685 of the captured file. The selftest linker crashes precede it.

The 284 BSP's `drivers/bus/spacemit-k3-espi.c` unconditionally calls `spacemit_espi_parse_dt()` from probe. The function takes `pdev->dev.of_node` and passes it to `of_range_to_resource()` at line 514. The OF parser calls `of_n_addr_cells(node)` before fetching the ranges property. Both build-5 captures show `a0=0` and a fault at address `0x68` on the first access to `np->parent`. The v12 firmware describes eSPI through ACPI. Linux enabled ACPI for both boots. Silence and input power on another attempt do not identify its kernel, boot mode or stopping point. **Qualification.** Neither build-5 boot reached the EC bind, UFS attach or userspace. Neither capture contained a literal `-517` or `K3BRSCHECK` line. Runtime module loading and `uname` were unreachable. Offline, all 1,794 modules extracted from the normal modules-core, modules and modules-extra RPMs had the intended vermagic. OpenSSL verified the detached signatures of NVMe, UFS and XFS against the certificate list extracted from the packaged kernel. These checks establish module integrity independently of the failed boot.

**Next kernel change.** Port the existing ACPI eSPI controller support to the packaged source. Keep the DT ranges fallback on DT systems, handle failed property reads before using the output, and let ACPI enumerate its children. Firmware supplies the controller MMIO resource and the two PR memory base properties. The Chrome EC transport also needs its RISC-V parent Kconfig dependency and the 284 EC allocation API. In a local RISC-V preflight, enabling the parent made the eSPI child resolve to built-in and exposed the BSP's call to the absent `cros_ec_device_alloc()`. Using the 284 allocation and protocol-buffer initialization produced all three EC objects. Hardware qualification still requires an EC event on pin 43 and independent UFS attach. [Existing controller implementation](../../patches/acpi-kernel/experiments/task4-espi-ec/spacemit-k3-espi-acpi.c) · [EC transport and ACPI IRQ lookup](../../patches/acpi-kernel/experiments/task4-espi-ec/cros_ec_espi-acpi.c)

Keep the gpioy kernel and matching initramfs as the recovery pair. For the release kernel, preserve the published ACPI pin numbers and share the existing SpacemiT driver's bank and IRQ logic. The package's effective GPIO configuration was already built-in. Its effective Chrome EC transport was absent despite the input configuration requesting it.

**Recovery verified on the board.** A one-time GRUB boot loaded `vmlinuz-dbg1-gpioy` and `initramfs-6.12.0-dbg1-gpioy.img`. Serial recorded `cros_ec_espi PRP0001:03: Chrome EC device registered` at 1.968898 s and UFS RPMB registration at 30.598216 s. SSH confirmed `6.12.0-dbg1-dbg1`, XFS root on `/dev/nvme0n1p2`, the TY7B-128 UFS disk, and live firmware DSDT SHA-256 `63bc318d9118daeec4e5c22871c7635ce6d69de85766f685b34f61ada5094747`. The on-disk BLS entry for build 5 also has no devicetree directive. The ESP DTB hashes to `46609974206c59b2ebcc37ddfc6740c39f5f65a404c404a86322bc6b564ea55e`, the RPM DTB to `8bea37f1486e44cc0793cc57099ee878f01cd9a38a170db0486c719405d2bf05`. Recovery was one-time. The saved entry still names the acpidebug BLS file and the observed GRUB menu initially highlighted stock 284.rv.0.
